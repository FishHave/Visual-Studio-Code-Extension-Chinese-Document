# 语言服务端扩展指南

如同您在[编程式语言特性](6.%20编程式语言特性.md)主题中所见，通过直接使用`languages.*`API实现语言特性是完全可行的。然而，语言服务端扩展提供额外的方式实现如此的语言支持。

本主题：
- 解释语言服务端扩展的优势。
- 带您体验使用[`Microsoft/vscode-languageserver-node`](https://github.com/microsoft/vscode-languageserver-node)库构建语言服务端的流程。您可以直接跳到[lsp-sample](https://github.com/microsoft/vscode-extension-samples/tree/main/lsp-sample)的代码。

## 为什么选择语言服务端

语言服务端是一种特殊的Visual Studio Code扩展，它驱动许多编程语言编辑体验。有了语言服务端，您可以实现自动补全、错误检查（诊断）、跳到定义和许多其他VS Code支持的[语言特性](6.%20编程式语言特性.md)。

然而，在实现对VS Code语言特性的支持时，我们发现下列常见问题。

首先，语言服务端通常使用它们原生编程语言实现，就产生了和使用Node.js运行时的VS Code整合的困难。

其次，实现语言特性耗时耗力。例如，为了正确校验文件，语言服务端需要解析大量文件，为其构建起抽象语法树并开始静态程序分析。这些操作可能导致大量CPU和内存开销，我们需要保证VS Code的表现不受影响。

最后，在多个代码编辑器整合多个语言工具耗费巨大精力。从语言工具的角度，它们需要适配不同的代码编辑器API。从代码编辑器的角度，它们不能指望语言工具有通用API。这让导致在`N`个代码编辑器中实现`M`个语言的语言支持有`M * N`的工作量。

为了解决这些问题，Microsoft规定了[语言服务端协议](https://microsoft.github.io/language-server-protocol/)，标准化语言工具和代码编辑器的交流。这样，只要它们通过语言服务端协议与代码编辑器交流，语言服务端可以实现任何语言，在它们自己的进程中运行，避免性能开销。不仅如此，遵从LSP的语言工具可以整合多个遵从LSP的代码编辑器，任何遵从LSP的代码编辑器可以采用多个遵从LSP的语言工具。LSP对语言工具提供者和代码编辑器供应者来说是双赢。

![](https://code.visualstudio.com/assets/api/language-extensions/language-server-extension-guide/lsp-languages-editors.png)

在本指南，我们会：

- 解释如何通过提供的[Node SDK](https://github.com/microsoft/vscode-languageserver-node)在VS Code中构建语言服务端扩展。

- 解释如何对语言服务端运行、调试、记录日志和测试。

- 帮您指明一些语言服务端进阶主题。

## 实现一个语言服务端

### 概览
在VS Code，语言服务端包含两部分：

- 语言客户端：由JavaScript或TypeScript编写的普通VS Code扩展。这个扩展可以访问所有的[VS Code命名空间API](/9.%20参考/1.%20VS%20Code%20API.md)。
- 语言服务端：单独运行在一个进程的语言分析工具。

如上面简要说明过，让语言服务端运行在独立的进程有两个好处：

- 分析工具可以实现任意语言，只要它能与遵从语言服务端协议的语言客户端交流。

- 因为语言分析工具通常产生大量CPU和内存开销，将它们运行在独立的进程避免了性能花费。

这边描述了运行两个语言服务端扩展的VS Code。HTML语言客户端和PHP语言客户端是用TypeScript编写的普通VS Code扩展。它们各自实例化相应的语言服务端，并通过LSP与之交流。尽管PHP语言语言服务端用PHP编写，它仍然可以通过LSP于PHP语言客户端交流。

![](https://code.visualstudio.com/assets/api/language-extensions/language-server-extension-guide/lsp-illustration.png)

本指南教会您如何使用[Node SDK](https://github.com/microsoft/vscode-languageserver-node)构建语言客户端或语言服务端。剩下的文档假设您已经熟悉了VS Code[扩展API](/9.%20参考/1.%20VS%20Code%20API.md)。

### 解释“语言客户端”

让我们看看`/package.json`，这描述了语言服务端的功能。两部分比较有意思：

首先，看看[`configuration`](/9.%20参考/2.%20贡献点.md)字段：

```json
"configuration": {
    "type": "object",
    "title": "Example configuration",
    "properties": {
        "languageServerExample.maxNumberOfProblems": {
            "scope": "resource",
            "type": "number",
            "default": 100,
            "description": "Controls the maximum number of problems produced by the server."
        }
    }
}
```

此字段为VS Code贡献了`configuration`设置。这个示例将解释这些设置如何在启动及设置变更时将设置发送给语言服务端。

**注意：**如果扩展兼容1.74.0以上的VS Code，您必须在`/package.json`中的[`activationEvents`](/9.%20参考/3.%20启用事件.md)字段中声明`onLanguage:plaintext`，以告知VS Code在普通文本文件打开时启用扩展（例如带有扩展名`.txt`的文件）：

```json
"activationEvents": []
```

实际的语言客户端源代码以及关联的`package.json`在`/client`文件夹中。`/client/package.json`中有意思的部分是它通过`engines`字段引用`vscode`扩展宿主API，并添加`vscode-languageclient`库的依赖：

```json
"engines": {
    "vscode": "^1.52.0"
},
"dependencies": {
    "vscode-languageclient": "^7.0.0"
}
```

已经提到过，客户端是作为普通VS Code扩展实现，能够访问所有VS Code命名空间API。

下面是关联的extension.ts文件内容，同时是**lsp-sample**扩展的入口：

```typescript
import * as path from 'path';
import { workspace, ExtensinoContext } from 'vscode';

import {
    LanguageClient,
    LanguageClientOptions,
    ServerOptions,
    TransportKind
} from 'vscode-languageclient/node'

let client: Language | undefined;

export async function activate(context: ExtensionContext) {
    // 服务端用node实现
    let serverModule = context.asAbsolutePath(path.join('server', 'out', 'server.js'));
    // 服务端调试选项
    // --inspect=6009: 用Node观察器模式运行服务端，以便VS Code连接服务端调试
    let debugOptions = { execArgv: ['--nolazy', '--inspect=6009'] };

    // 如果扩展在调试模式下启动，那么使用调试服务端选项
    // 否则使用运行选项
    let serverOptions: ServerOptions = {
        run: { module: serverModule, transport: TransportKind.ipc },
        debug: {
            module: serverModule,
            transport: TransportKind.ipc,
            options: debugOptions
        }
    };

    // 控制语言客户端的选项
    let clientOptions: LanguageClientOptions = {
        // 为普通文本文档注册服务端
        documentSelector: [{ scheme: 'file', language: 'plaintext' }],
        synchronize: {
            // 提醒服务端工作空间中'.clientrc文件有更改
            fileEvents: workspace.createFileSystemWatcher('**/.clientrc')
        }
    };

    // 创建语言客户端并启动客户端。
    client = new LanguageClient(
        'languageServerExample',
        'Language Server Example',
        serverOptions,
        clientOptions
    );

    // 启动客户端，同时启动服务端。
    await client.start();
}

exoprt async function deactivate() {
    await client?.dispose();
    client = undefined;
}
```

### 解释“语言服务端”

**注意：**从GitHub仓库复制的“服务端”实现拥有最终完整引导实现。创建新的`server.ts`或修改复制的版本内容跟随引导。

在本例中，服务端也由TypeScript实现，并且使用Node.js执行。由于VS Code已经搭载了Node.js运行时，无需提供您自己的运行时，除非您对运行时有特别要求。

语言服务端代码位于`/server`，服务端`package.json`文件中最有意思的部分是：

```json
"dependencies": {
    "vscode-languageserver": "^7.0.0",
    "vscode-languageserver-textdocument": "^1.0.1"
}
```

这拉取了`vscode.languageserver`库。

下面的服务端实现使用了上面提供的文本文档管理器，通过从VS Code逐步发送差异给客户端保持文本文档的持续同步。

```typescript
import {
    createConnection,
    TextDocument,
    Diagnostic,
    DiagnosticSeverity,
    ProposedFeatures,
    InitializeParams,
    DidChangeConfigurationNotification,
    CompletionItem,
    CompletionItemKind,
    TextDocumentPositionParams,
    TextDocumentSyncKind,
    InitializeResult
} from 'vscode-languageserver/node';

import { TextDocument } from 'vscode-langaugeserver-textdocument';

// 创建服务端的连接，使用Node IPC作为通信。
// 同时包含所有预览/推荐LSP特性。
let connection = createConnection(ProposedFeatures.all);

// 创建简单文本文档管理器
let documents: TextDocuments<TextDocument> = new TextDocuments(TextDocument);

let hasConfigurationCapability: boolean = false;
let hasWorkspaceFolderCapability: boolean = false;
let hasDiagnosticRelatedInformationCapability: boolean = false;

connection.onInitialize((params: InitializeParams) => {
    let capabilities = params.capabilities;

    // 客户端是否支持“workspace/configuration”请求？
    // 如果不是，我们回退使用全局设置。
    hasConfiguraionCapability = !!(
        capabilities.workspace && !!capabilities.workspace.configuration
    );
    hasWorkspaceFolderCapabilities = !!(
        capabilities.workspace && !!capabilities.workspace.workspaceFolders
    );
    hasDiagnosticRelatedInformationCapability = !!(
        capabilities.textDocument &&
        capabilities.textDocument.publishDiagnostics &&
        capabilities.textDocument.publishDiagnostics.relatedInformation
    );

    const result: InitializeResult = {
        capabilities: {
            textDocumentSync: TextDocumentSyncKind.Incremental,
            // 告诉客户端服务端支持代码补全
            completionProvider: {
                resolveProvider: true
            }
        }
    };
    if (hasWorkspaceFolderCapability) {
        result.capabilities.workspace = {
            workspaceFolders: {
                supported: true
            }
        };
    }
    return result;
});

connection.onInitialized(() => {
    if (hasConfigurationCapability) {
        // 注册所有配置更改
        connection.client.register(DidChangeConfigurationNotification.type, undefined);
    }
    if (hasWorkspaceFolderCapability) {
        connection.workspace.onDidChangeWorkspaceFolders(_event => {
            connection.console.log('Workspace folder change event received.');
        });
    }
});

// 示例设置
interface ExampleSettings {
    maxNumberOfProblems: number;
}

// 全局设置，当客户端不支持`workspace/configuration`请求时使用。
// 请注意，在使用此服务端和本示例中提供的客户端时，情况并非如此。
// 然而别的客户端亦如此。
const defaultSettings: ExampleSettings = { maxNumberOfProblems: 1000 };
let globalSettings: ExampleSettings = defaultSettings;

// 缓存所有打开文档的设置
let documentSettings: Map<string, Thenable<ExampleSettings>> = new Map();

connection.onDidChangeConfiguration(change => {
    if (hasConfigurationCapability) {
        // 重置所有缓存的文档设置
        documentSettings.clear();
    } else {
        globalSettings = <ExampleSettings>(
            (change.settings.languageServerExample || defaultSettings)
        );
    }

    // 重新校验所有打开的文本文档
    documents.all().foreach(validateTextDocument);
});

function getDocumentSettings(resource: string): Thenable<ExampleSettings> {
    if (!hasConfigurationCapability) {
        return Promise.resolve(globalSettings);
    }
    let result = documentSettings.get(resource);
    if (!result) {
        result = connection.workspace.getConfiguration({
            scopeUri: resource,
            section: 'languageServerExample'
        });
        documentSettings.set(resource, result);
    }
    return result;
}

// 只保留打开的文档设置
documents.onDidClose(e => {
    documentSettings.delete(e.document.uri);
});

// 文本文档的内容已修改。在文本
// 文档第一次打开或其内容更改时发出本事件
documents.onDidChangeContent(change => {
    validateTextDocument(change.document);
});

async function validateTextDocument(textDocument: TextDocument): Promise<void> {
    // 在这个简单的例子中，我们为所有运行的校验获取设置。
    let settings = await getDocumentSettings(textDocument.uri);

    // 校验器为所有长度大于等于2的大写单词创建诊断
    let text = textDocument.getText();
    let pattern = /\b[A-Z]{2,}\b/g;
    let m: RegExpExecArray | null;

    let problems = 0;
    let diagnostics: Diagnostic[] = [];
    while ((m = pattern.exec(text)) && problems < settings.maxNumberOfProblems>) {
        problems++;
        let diagnostic: Diagnostic = {
            severity: DiagnosticSeverity.Warning,
            range: {
                start: textDocument.positionAt(m.index),
                end: textDocument.positionAt(m.index + m[0].length)
            },
            message: `${m[0]} is all uppercase.`,
            source: 'ex'
        };
        if (hasDiagnosticRelatedInformationCapability) {
            diagnostic.relatedInformation = [
                {
                    location: {
                        uri: textDocument.uri,
                        range: Object.assign({}, diagnostic.range)
                    },
                    message: 'Spelling matters'
                },
                {
                    location: {
                        uri: textDocument.uri,
                        range: Object.assign({}, diagnostic.range)
                    },
                    message: 'Particularly for names'
                }
            ];
        }
        diagnostics.push(diagnostic);
    }

    // 为VS Code发送演算后的诊断
    connection.sendDiagnostics({ uri: textDocument.uri, diagnostics });
}

connection.onDidChangeWatchedFiles(_change => {
    // 监视VS Code中已经更改的文件
    connection.console.log('We received a file change event');
});

// 这边的处理器提供补全项目的初始化列表
connection.onCompletion(
    (_textDocumentPosition: TextDocumentPositionParams): CompletionItem[] => {
        // 传递的参数包含代码补全发送的请求
        // 在文本文档中的位置。在此例中我们忽略
        // 这个信息，并永远提供相同的补全项目。
        return [
            {
                label: 'TypeScript',
                kind: CompletionItemKind.Text,
                data: 1
            },
            {
                label: 'JavaScript',
                kind: CompletionItemKind.Text,
                data: 2
            }
        ];
    }
);

// 这边的处理器处理补全列表中选中物品的其他信息
connection.onCompletionResolve(
    (item: CompletionItem): CompletionItem => {
        if (item.data === 1) {
            item.detail = 'TypeScript details';
            item.documentation = 'TypeScript documentation';
        } else if (item.data === 2) {
            item.detail = 'JavaScript details';
            item.documentation = 'JavaScript documentation';
        }
        return item;
    }
);

// 使文本文档管理器监听连接
// 的打开、更改以及关闭文本文档事件
documents.listen(connection);

// 监听连接
connection.listen();
```

### 添加简易校验

我们向文本文档内容变动时调用的文本文档管理器添加监听器，来为服务端添加文档校验。校验文档的时机取决于服务端。在这个示例实现中，服务端校验普通文本文档，并标记所有全大写单词出现的地方。相关代码片段如下：

```typescript
// 文本文档内容已变更。
// 当文本文档第一次被打开或其内容变动时触发此事件
documents.onDidChangeContent(async change => {
    let textDocument = change.document;
    // 在本例中，我们每次运行校验时获取设置
    let settings = await getDocumentSettings(textDocument.uri);

    // 校验器为所有长度大于等于2的单词创建诊断
    let text = textDocument.getText();
    let pattern = /\b[A-Z]{2,}\b/g;
    let m: RegExpExecArray | null;

    let problems = 0;
    let diagnostics: Diagnostic[] = [];
    while ((m = pattern.exec(text)) && problems < settings.maxNumberOfProblems) {
        problems++;
        let diagnostic: Diagnostic = {
            severity: DiagnosticSeverity.Warning,
            range: {
                start: textDocument.positionAt(m.index);
                end: textDocument.positionAt(m.index + m[0].length)
            },
            message: `${m[0]} is all uppercase`,
            souce: 'ex'
        };
        if (hasDiagnosticRelatedInformationCapability) {
            diagnostic.relatedInformation = [
                {
                    location: {
                        uri: textDocument.uri,
                        range: Object.assign({}, diagnostic.range)
                    },
                    message: 'Spelling matters'
                },
                {
                    location: {
                        uri: textDocument.uri,
                        range: Object.assign({}, diagnostic.range)
                    },
                    message: 'Particularly for names'
                }
            ];
        }
        diagnostics.push(diagnostic);
    }

    // 向VS Code发送演算后的诊断
    connection.sendDiagnostics({ uri: textDocument.uri, diagnostics });
});
```

### 在服务端使用配置设置
在编写扩展的客户端部分，我们已经定义设置控制报告问题的最大数量。我们也需要在服务端侧编写代码，从客户端读取这些设置：

```typescript
function getDocumentSettings(resource: string): Thenable<ExampleSettings> {
    if (!hasConfigurationCapability) {
        return Promise.resolve(globalSettings);
    }
    let result = documentSettings.get(resource);
    if (!result) {
        result = connection.workspace.getConfiguration({
            scopeUri: resource,
            section: 'languageServerExample'
        });
        documentSettings.set(resource, result);
    }
    return result;
}
```

我们现在所需做的唯一一件事是监听服务端侧的配置更改，如果设置发生变动，重新校验打开的文本文档。为了能够复用文档更改事件处理的校验逻辑，我们提取代码到`validateTextDocument`函数，并修改代码以遵循`maxNumberOfProblems`变量：

```typescript
async function validateTextDocument(textDocument: TextDocument): Promise<void> {
    // 在这个简单的案例中，我们在每次运行校验时获取设置。
    let settings = await getDocumentSettings(textDocument.uri);

    // 校验器会为所有长度在2以上的大写单词创建诊断
    let text = textDocument.getText();
    let pattern = /\b[A-Z]{2,}\b/g;
    let m: RegExpExecArray | null;

    let problems = 0;
    let diagnostics: Diagnostic[] = [];
    while ((m = pattern.exec(text)) && problems < settings.maxNumberOfProblems) {
        problems++;
        let diagnostic: Diagnostic = {
            severity: DiagnosticSeverity.Warning,
            range: {
                start: textDocument.positionAt(m.index),
                end: textDocument.positionAt(m.index + m[0].length)
            },
            message: `${m[0]} is all uppercase`,
            source: 'ex'
        };
        if (hasDiagnosticRelatedInformationCapability) {
            diagnostic.relatedInformation = [
                {
                    location: {
                        uri: textDocument.uri,
                        range: Object.assign({}, diagnostic.range)
                    },
                    message: 'Spelling matters'
                },
                {
                    location: {
                        uri: textDocument.uri,
                        range: Object.assign({}, diagnostic.range)
                    },
                    message: 'Particularly for names'
                }
            ];
        }
        diagnostics.push(diagnostic);
    }

    // 向VS Code发送演算后的诊断
    connection.sendDiagnostics({ uri: textDocument.uri, diagnostics });
}
```

配置更改通过向连接添加它的通知处理器进行处理。相关的代码如下：

### 添加额外的语言特性
语言服务端通常实现的首要特性是文档校验。在这种意义上，即便是静态代码检查工具也可以算是一种语言服务端，并且在VS Code中，静态代码检查工具确实通常用语言服务端实现（参考[eslint](https://github.com/microsoft/vscode-eslint)和[jslint](https://github.com/microsoft/vscode-jshint)）。但是，语言服务端不止如此。它们可以提供代码补全、查找所有引用或者转到定义。下面的示例代码向服务端添加了代码补全。它建议两个单词“TypeScript”和“JavaScript”。

```typescript
// 这边的处理器提供补全项目的初始化列表
connection.onCompletion(
    (_textDocumentPosition: TextDocumentPositionParams): CompletionItem[] => {
        // 传递的参数包含代码补全发送的请求
        // 在文本文档中的位置。在此例中我们忽略
        // 这个信息，并永远提供相同的补全项目。
        return [
            {
                label: 'TypeScript',
                kind: CompletionItemKind.Text,
                data: 1
            },
            {
                label: 'JavaScript',
                kind: CompletionItemKind.Text,
                data: 2
            }
        ];
    }
);

// 这边的处理器处理补全列表中选中物品的其他信息
connection.onCompletionResolve(
    (item: CompletionItem): CompletionItem => {
        if (item.data === 1) {
            item.detail = 'TypeScript details';
            item.documentation = 'TypeScript documentation';
        } else if (item.data === 2) {
            item.detail = 'JavaScript details';
            item.documentation = 'JavaScript documentation';
        }
        return item;
    }
);
```

`data`字段用于为分析处理器的补全项目指定唯一标识符。数据属性对协议透明。因底层通过协议传递的消息是基于JSON，数据字段仅持有能够序列化为JSON、从JSON反序列化的数据。

现在少了的东西只有告诉VS Code服务端支持代码补全请求。为此，在初始化处理器中标记相关的能力

```typescript
connection.onInitialize((params): InitializeResult => {
    ...
    return {
        capabilities: {
            ...
            // 告知客户端服务端支持代码补全
            completionProvider: {
                resolveProvider: true
            }
        }
    };
});
```

### 测试语言服务端
为了创建高质量的语言服务端，我们需要构建一个合适的测试集覆盖其功能。测试语言服务端有两种常用方法：

- 单元测试：如果您想要测试语言服务端特定的功能，这能起很大作用，您可以模拟所有发送给它信息。VS Code的[HTML](https://github.com/microsoft/vscode-html-languageservice) / [CSS](https://github.com/microsoft/vscode-css-languageservice) / [JSON](https://github.com/microsoft/vscode-json-languageservice) 语言服务端采用这种测试方式。LSP npm模块也使用这种方式。参考[此处](https://github.com/microsoft/vscode-languageserver-node/blob/main/protocol/src/node/test/connection.test.ts)查看使用npm协议模块编写的单元测试。
- 端对端测试：与[VS Code扩展测试](/7.%20测试与发布/1.%20测试扩展.md)。这种方法的好处是它通过在工作空间中初始化VS Code实例，打开文件并启用语言客户端与服务端，并运行[VS Code命令](/9.%20参考/5.%20内建命令.md)运行测试。如果您难以或不可能模拟某些文件、设置或依赖（比如`node_modules`）优先采用这种方法。广为人知的[Python](https://github.com/microsoft/vscode-python)扩展采用这种方式测试。

使用任何您选择的测试框架运行单元测试都是可能的。这边我们介绍如何对语言服务端扩展完成端对端测试。

打开`.vscode/launch.json`，您可以找到`E2E`测试目标：

```json
{
    "name": "Language Server E2E Test",
    "type": "extensionHost",
    "request": "launch",
    "runtimeExecutable": "${execPath}",
    "args": [
        "--extensionDevelopmentPath=${workspaceRoot}",
        "--extensionTestsPath=${workspaceRoot}/client/out/test/index",
        "${workspaceRoot}/client/testFixture"
    ],
    "outFiles": ["${workspaceRoot}/client/out/test/**/*.js"]
}
```

如果您运行这个调试目标，它会使用`client/testFixture`作为活跃工作空间启动VS Code实例。VS Code随即依次执行`client/src/test`中的所有测试。这里给条调试提示，您可以在`client/src/test`的TypeScript文件设置断点使它们被触发。

让我们看看`completion.test.ts`文件：

```typescript
import * as vscode from 'vscode';
import * as assert from 'assert';
import { getDocUri, activate } from './helper';

suite('Should do completion', () => {
    const docUri = getDocUri('completion.txt');
    test('Completes JS/TST in txt file', async () => {
        await testCompletion(docUri, new vscode.Position(0, 0), {
            items: [
                { label: 'JavaScript', kind: vscode.CompletionItemKind.Text },
                { label: 'TypeScript', kind: vscode.CompletionItemKind.Text }
            ]
        });
    });
});

async function testCompletion(
    docUri: vscode.Uri,
    position: vscode.Position,
    expectedCompletionList: vscode.CompletionList
) {
    await activate(docUri);

    // 执行命令 `vscode.executeCompletionItemProvider`模拟触发补全
    const actualCompletionList = (await vscode.commands.executeCommand(
        'vscode.executeCompletionItemProvider',
        docUri,
        position
    )) as vscode.CompletionList;

    assert.ok(actualCompletionList.items.length >= 2);
    expectedCompletionList.items.forEach((expectedItem, i) => {
        const actualItem = actualCompletionList.items[i];
        assert.equal(actualItem.label, expectedItem.label);
        assert.equal(actualItem.kind, expectedItem.kind);
    });
}
```

在这个测试中，我们》：
- 启用扩展
- 用一个URI和坐标模拟补全触发运行命令`vscode.executeCompletionItemProvider`。
- 根据期望的补全项，断言返回的补全项。

让我们深入`activate(docURI)`函数。它定义在`client/src/test/helper.ts`：

```typescript
import * as path from 'path'

export let doc: vscode.TextDocument;
export let editor: vscode.TextEditor;
export let documentEol: string;
export let platformEol: string;

/**
 * 启用 vscode.lsp-sample扩展
 */
export async function activate(docUri: vscode.Uri) {
    // extensionId是package.json中的`publisher.name`
    const ext = vscode.extensions.getExtension('vscode-samples.lsp-sample')!;
    await ext.activate();
    try {
        doc = await vscode.workspace.openTextDocument(docUri);
        editor = await vscode.window.showTextDocument(doc);
        await sleep(2000); //等待服务都安启用
    } catch (e) {
        console.error(e);
    }
}

async function sleep(ms: number) {
    return new Promise(resolve => setTimeout(resolve, ms));
}
```

在启用部分，我们：
- 使用定义在`package.json`中的`{publisher.name}.{extensionId}`获取扩展。
- 打开特定文档，在活跃文本编辑器中显示。
- 休眠两秒，这样我们能确保语言服端已经初始化。

准备完成后，我们可以运行语言特性相关的[VS Code命令](/9.%20参考/5.%20内建命令.md)，并根据返回结果断言。

### 其他语言服务端特性
下面是除了代码补全外语言服务端目前支持的语言特性：
- *文档高亮*：高亮文本文档中所有的“equal”符号。
- *悬停提示*：为文本文档中选中的符号提供悬停提示。
- *签名帮助*： 为文本文档中选中的符号提供签名帮助。
- *转到定义*：提供文本文档中选中的符号的定义支持。
- *转到类型定义*： 为文本文档中选中的符号提供转到类型/接口定义支持。
- *转到实现*：为文本文档中选中的符号提供转到实现定义支持。
- *查找引用*：查找整个项目中对文本文档选中符号的引用。
- *列举文档符号*：列举文本文档中定义的所有符号。
- *列举工作空间符号*：列举项目范围内的符号。
- *代码操作*：为给定文本文档和范围演算命令并执行（通常是美化或重构）。
- *代码透镜*：为给定的文本文档演算代码透镜统计。
- *文档格式化*：这包括文档、文档范围和类型的格式化。
- *重命名*：项目范围内符号重命名。
- *文档链接*：在文档内演算并处理链接。
- *文档颜色*：在编辑器中，计算并处理文档中颜色以提供取色器。

[编程性语言特性](6.%20编程式语言特性.md)主题介绍了上面的每一种语言特性，并提供通过语言服务端协议或直接在扩展中使用扩展API实现它们的方法。
